BARDAHL — объединённое приложение автосервиса (НОВЫЙ ПРОЕКТ)

Это отдельный проект. Он использует новый Supabase:
https://tbkzbypuxrgqwpledwuk.supabase.co
Публичный Publishable key уже внесён в index.html. Service role/secret key в браузер не добавляется.

СОСТАВ
- index.html — PWA, вход по email/паролю, очередь, каталог 35 услуг, заказы и отчёты.
- setup.sql — схема БД, серверные проверки ролей и политики безопасности (RLS).
- create_profiles_template.sql — привязка аккаунтов к ролям после создания пользователей в Supabase Auth.
- manifest.webmanifest, sw.js, icon*.svg — установка приложения.

РОЛИ
- 9 мастеров: очередь и создание/просмотр/редактирование собственных заказов.
- Менеджер: только очередь, изменение позиций/сброс кругов; заказы и финансы закрыты на уровне БД.
- Руководитель: очередь и полная статистика/история всех заказов.

ПОРЯДОК УСТАНОВКИ
1. В новом Supabase откройте SQL Editor и выполните setup.sql целиком.
2. Supabase -> Authentication -> Users: вручную создайте 11 пользователей с email и временными паролями. Публичную регистрацию отключите. Не используйте один пароль для всех.
3. Откройте create_profiles_template.sql, замените каждый REPLACE-...@example.com на соответствующий email созданного пользователя, затем выполните этот SQL в SQL Editor. Проверьте, что запрос показывает 11 строк.
4. В новом отдельном GitHub-репозитории загрузите ВСЕ файлы из этой папки в корень. В Settings -> Pages включите публикацию из ветки main, папка /(root).
5. Откройте опубликованный HTTPS-сайт. Каждый пользователь входит своим email и временным паролем; при первом входе приложение потребует новый пароль минимум из 10 символов.

БЕЗОПАСНОСТЬ И ВАЖНО
- Не выполняйте SQL в старом проекте Supabase: этот архив предназначен только для нового проекта tbkzbypuxrgqwpledwuk.
- Не публикуйте пароль БД, Secret key или service_role key. В index.html находится только Publishable key.
- Перед загрузкой в реальную эксплуатацию желательно проверить весь SQL в тестовом проекте и создать резервную копию. Подключение к живому Supabase из этой среды не тестировалось.
- Временный пароль считается использованным после смены через приложение; флаг must_change_password хранится в user_profiles. Создание пользователей и назначение ролей выполняет владелец проекта вручную.
- Старые локальные заказы из прежнего приложения автоматически не переносятся. Для переноса сначала экспортируйте JSON из старого приложения; импорт делайте после входа руководителя/мастера в новую систему и только если нужно сохранить историю.
